# 任务交接与裁决模板

这些模板用于开发团队交接，不存储招聘账号、会话凭据或个人原始资料。只在任务发生时创建对应记录，不要求提前生成空目录和占位文件。

## 1. 任务卡

保存到 `docs/workflow/tasks/<TASK-ID>.md`；执行者只有一个，产品、架构和 QA可作为协作者。

```yaml
task_id: T04
title: JD条件解析与事实证据匹配
phase: 1
priority: P0
status: draft
owner_role: implementation
reviewer_role: independent_qa
dependencies: [T01, T02]
input_versions:
  prd: 待任务开始时填写真实文件版本
  contract: 待固定契约后填写
write_scope:
  - 待分配的具体文件路径
acceptance_ids: []
execution_budget: 待执行前估算
blocked_reason: null
evidence_paths: []
```

任务正文说明用户问题、范围和非本期内容、输入样例、输出样例、错误处理、逐条验收、依赖、文件归属和恢复方法。示例值不是实际已派发任务；验收条目、版本和路径未填写完整时不能设置为 ready。

## 2. 交付通知

| 字段 | 填写要求 |
|---|---|
| task_id 与 action | 说明需要接收方做验证、提供输入、裁决还是集成 |
| artifact_version | 精确 commit、diff 或文件哈希，禁止只写“最新代码” |
| contract_version | 对应输入输出和错误约定版本 |
| changed_files | 文件路径、修改目的和接口影响 |
| evidence_paths | 可复跑命令、操作记录、截图和产物，分别标明自测/独立验证 |
| known_gaps | 未验证、失败、范围外和需用户输入的事项 |
| next_owner | 接收职责与依赖，不能把任务结束等同于整个项目结束 |

由项目编排工具发送通知或由主理人更新共享台账。通知授权遵循所在工具的限制；不会仅因模板存在而自动创建聊天、消息、邮件或后台任务。

## 3. 审查报告

保存到 `docs/workflow/reviews/<REVIEW-ID>.md`。

| 字段 | 填写要求 |
|---|---|
| review_id、task_id、run_id | 与交付和运行对应 |
| independence | `author_self_review` 或 `independent_qa`；说明是否参与实现 |
| reviewed_version | 审查的固定变更快照及输入版本 |
| verdict | `pass`、`changes_requested` 或 `coverage_incomplete` |
| findings | 每条有问题ID、S级别、验收ID、位置、复现、期望、实际、影响和建议 |
| executed_checks | 实际执行的方法和结果，未执行项单独说明 |
| residual_risk | 范围空白、未覆盖网站或样例，不能用“全部测试通过”遮盖 |

独立审查阶段只提出结论，不直接修改实现。复验保留原报告并增加新的运行和结论；作者负责实现阶段修复。

## 4. 争议记录

保存到 `docs/workflow/disputes/<DISPUTE-ID>.md`。

| 字段 | 填写要求 |
|---|---|
| dispute_id、task_id、finding_id | 同一问题保持稳定编号 |
| disputed_claim | 写出真正有分歧的行为、标准或范围 |
| agreed_baseline | 双方接受的需求和契约版本 |
| developer_evidence / qa_evidence | 各自证据、实际结果与证据空白 |
| arbiter / conflict_of_interest | 裁决职责，以及是否参与被争议的实现或决策 |
| minimal_experiment | 如事实不明，写一个能区分两个主张的最小实验 |
| decision | 修复、补证、延期、范围调整或交用户；附依据 |
| follow_up | 负责人、受影响验收、复验结果和再开条件 |

“主理人认为没问题”不是证据。涉及权限、事实和真实投递的关键缺陷不能只凭日程压力延期。

## 5. 决策与运营反馈

决策记录保存到 `docs/workflow/decisions/<ADR-ID>.md`，包含问题、备选方案、验证证据、结论、契约影响、兼容和回退、审批范围。未验证的选择注明假设，后续依据实际结果修订。

反馈保存到 `docs/workflow/feedback/<FEEDBACK-ID>.md`，包含用户类别和任务、产品版本、原人工流程、观察到的动作、耗时和纠错、用户原话、解释假设及建议任务。反馈中只保存必要脱敏内容；产品从反馈提出新需求，主理人排入下一轮，不能让运营直接改需求基线。
